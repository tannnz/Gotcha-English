# 开发流程

## 新增仓库文件

逐项审核新增文件，确认适合纳入仓库后，将对应路径显式加入 `.gitignore` 的放行规则。

## 修改或新增 Skill

修改前阅读相关 Skill 正文和它引用的模板、支持资源。直接编辑 `skills/` 中的源文件；新增 Skill 放入 `skills/<name>/SKILL.md`，在文件头部填写与目录名一致的 `name` 和单行 `description`。Skill 名称使用小写字母、数字和连字符；支持资源放在该 Skill 目录内，通过相对路径引用。

学习记录格式的唯一维护源是 `skills/setup-learning-space/references/record-format.md`。修改字段、正文或证据规则时先改这里，再执行 `python3 scripts/package-plugin.py --sync-record-format`；收录 Skill 中的同名文件是生成副本。检查会拒绝不同步的副本。文档中的格式版本覆盖字段和正文，格式不兼容的修改需要同步更新支持规则和维护方案，不能只升级插件版本。

## 修改插件元数据

修改插件元数据时，按[架构](architecture.md)找到维护源，编辑后运行 `python3 scripts/package-plugin.py --sync-metadata` 同步生成文件。

## 验证改动

修改内容、元数据或工具后，运行以下检查。

```sh
python3 scripts/package-plugin.py --check
python3 -m unittest discover -s tests
git diff --check
git status --short
```

仅修改文档时，运行 `git diff --check` 并检查文件差异与工作区状态。

`--check` 检查元数据和共用格式是否同步，并验证市场路径、Skill 格式和资源引用。检查不生成 ZIP。

使用虚构材料检查修改后的 Skill 行为、引用资源和输出是否符合该 Skill 的规则。测试材料应放在测试创建的临时目录中，不作为正式功能提交。

修改收录行为后，用虚构对话检查收录判断、新旧问题归并、跨对话重复材料、计数与日期、状态变化及检索缺口。打包测试只验证资源和生成关系；没有实际宿主和数据库验证时应注明这一限制。

## 在 Codex 验证测试版

1. 从 `beta` 新建功能分支，在本地修改和检查。提交时保持每项功能的改动可单独合入正式版。
2. 通过拉取请求将通过检查的改动合入 `beta`。
3. 按 [README](../README.md#测试版) 安装或更新测试版。
4. 在 Codex 桌面端开启新对话，选择测试版，用虚构材料验证受影响的 Skill。

正式版从 `main` 读取内容。测试通过后，从 `main` 新建分支，挑选已验证的功能提交，向 `main` 提交拉取请求。测试版的插件名称和市场配置留在 `beta`。正式版安装者刷新后就会收到合入的内容。

## 验收双版本安装

1. 按 [README](../README.md#在-codex-安装和更新插件) 在同一 Codex 客户端安装两版。旧的 `gotcha-english-local` 市场（本机目录或旧 GitHub 配置）使用独立的市场名。保留旧安装，验证新版本时先停用旧插件。
2. 分别开启新对话，选择正式版和测试版。用虚构材料调用同一个 Skill，核对调用来源。若两版的输出相同，查看客户端显示的插件来源或调用记录。
3. 测试版有新提交后，仅更新测试版。在新对话中确认测试版收到改动，正式版仍使用原来的内容。

如果两版同时启用会调用错误版本，保留两版安装，每次只启用一版，并重新验证。如果切换后仍会调用错误版本，保留旧本机安装并暂停切换。验收通过后可移除旧本机 Codex 市场和安装。

更新未生效时，检查市场来源、GitHub 分支和已安装的插件。在新对话中重试，必要时按客户端支持的方式重新安装。排查时可读取缓存核对内容。

分别记录结构检查、安装和调用结果，未完成的项目标为待验证。Claude Code 结构检查使用可用的官方插件验证器；实际调用结果需单独验证。
